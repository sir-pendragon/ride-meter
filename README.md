# 自転車旅メーター（Web試作版）と自転車旅ノート

- 自転車旅メーター: `meter/`
- 自転車旅ノート: `note/`
(2つのアプリが別のアイコンでホーム画面に入るよう、置き場所を分けています)

Pixel(Android)のChromeで使う、サイクルコンピューターの試作版です。

## できること
- 速度・距離・走行時間・平均/最高速度・GPS高度・獲得標高・経過時間・時刻・ルート残りなどの表示
- 計測画面のレイアウト変更：画面を複数枚つくり左右スワイプで切替。各マスの項目と大きさ(大・中・小)、並び順を変更できる（記録・設定 →「計測画面のレイアウト」）
- 走行記録の端末内保存（ページを閉じても、次に開いたとき一時停止状態で復元）
- GPX書き出し（自転車旅ノートにそのまま取り込める形式。写真・地点は `<wpt>` として出力）
- ルート案内：GPXを読み込み、残り距離とコースアウト警告（振動＋赤い帯、既定50m・3回連続で警告）
- 走行中の「写真」「地点」記録（その時点の位置と時刻を残す）
- 地図（地理院タイル / OpenStreetMap）
- シミュレーション走行（室内での動作確認用）

## 公開手順（GitHub Pages、Windowsのブラウザだけで可）
1. GitHubで新しいリポジトリを作成（例: `ride-meter`、Public）。
2. 「Add file → Upload files」で、このフォルダの中身をすべてアップロード
   （`index.html` `core.js` `sw.js` `manifest.webmanifest` `icon-192.png` `icon-512.png` `leaflet/` フォルダ）。
3. Settings → Pages → Branch を `main` / `(root)` にして Save。
4. 数分後に表示される `https://<ユーザー名>.github.io/ride-meter/meter/` を Pixel の Chrome で開く。
5. 位置情報を「許可」。Chromeのメニュー →「ホーム画面に追加」でアプリのように起動できます。

※ GPSはHTTPSのページでしか使えないため、PCのファイルを直接開く方法では動きません。

## 制約（試作版の時点で分かっていること）
- **画面を消すと記録が途切れます。** Webアプリはバックグラウンドで位置を取り続けられません。
  既定で画面を点けたままにします（バッテリー消費が増えます）。途切れた区間は直線でつなぎ、回数を表示します。
  これを根本的に解決するのが、次の段階のネイティブAndroidアプリです。
- **高度はGPSの楕円体高です。** 標高より数十m高く出ます（日本ではおおむね30〜40m。場所で異なる）。
  設定の「高度の補正値」にその地域のジオイド高を負の値で入れると標高に近づきます。獲得標高は補正値の影響を受けません。
- **距離の計算方法**: 端末がGPS速度を返す場合は「速度×時間」で積分します（ノイズ入りの模擬データで誤差0.2%以内）。
  返さない場合は平滑化した位置から計算し、模擬データで誤差+0.5〜+10%（低速・測位が粗いほど過大）。
  Pixel実機がGPS速度を返すかは未確認です。試走して「最高速度」が0.0のままなら、速度が返っていません。
- **写真ボタンで撮った写真は縮小版をアプリ内に保存するだけです。** 端末のギャラリーには残らない場合があります。
  きれいな写真は普段のカメラアプリで撮り、走行中は「地点」ボタンで場所だけ残す使い方を推奨します。
- **地図は電波のある場所でのみ表示されます。** アプリ本体は圏外でも起動・記録できます。
- データは端末のブラウザ内だけに保存されます。Chromeの「サイトデータを削除」で消えるので、走行後はGPXを書き出してください。

## 自転車旅ノート(`note/`)
旅の記録ノート。`https://<ユーザー名>.github.io/ride-meter/note/` で開き、Chromeのメニュー →「ホーム画面に追加」でアプリのように起動できます。
- 記録(軌跡・キャンプ場)は **この端末のブラウザ内(IndexedDB)にだけ保存** され、どこにも送信されません。
- 一覧画面の「全データを書き出す」「ファイルから読み込む」でバックアップ・端末移行ができます。旅1件だけの書き出し(家族への共有用)は旅の画面から。
- Chromeの「サイトデータを削除」で消えるので、ときどき書き出してください。

## 自転車ルート予想(`route/`)
スタート・経由地(休憩所など)・ゴールを置くと、プルダウンで「最小獲得標高」か「最大獲得標高」を選ぶと、その条件のルートを1本計算します(候補を同時に問い合わせ、その中から選びます。舗装率は選んだルートだけ調べます)。距離・獲得標高・平均勾配・最大勾配・舗装率(推定)と標高プロファイルを表示し、GPXで保存できます。
- 地図: 国土地理院タイル(将来Googleマップに差し替え予定)。ルート計算: Valhalla公開サーバー(OpenStreetMap)。標高: 国土地理院DEM10Bタイル。場所検索: Nominatim。
- Googleマップの自転車ルート検索は日本で提供されていないため、ルート計算には使っていません。

### 条件の種類と、候補の広げ方(route-v57)
- 条件: 最小獲得標高 / 最大獲得標高 / 自転車ルートを優先 / **快適・絶景** / **最短距離ルート**。距離の上限は、最小獲得標高・自転車ルート優先・快適・絶景が「最短の1.5倍まで」、最大獲得標高の基本候補は上限なし(距離上限の入力欄はありません)。
- **最短距離ルート**: Valhalla の `shortest`(距離だけで選ぶ)を指定して1回問い合わせ、通行止めを通らない候補の中で一番短いものを選ぶ。追加探索はしない。坂・路面は考慮しないため、急な坂や未舗装を通ることがある(画面に注意書きを出す)。公開サーバーで同じ区間(飯能駅→西武秩父駅)が、自転車ルート優先 38.2 km に対し 34.7 km になることを確認(2026-10-15)。
- **快適・絶景**: 静かさ45% + 激坂の少なさ35% + 景観20% の総合スコア(0〜100点)。各指標は固定の基準で0〜1にし、内訳の値も表示します。
  - 静かさ(推定): 交通量の実測ではなく、道路種別・車線数・速度制限・自転車レーンからの代理指標です。自転車で走れると確認できない区間(階段・フェリー・属性不明)は静かさに数えず、割合を表示します。
  - 激坂: 100m・200mの区間の平均勾配で、9%以上・12%以上・15%以上と段階的に強くペナルティ(登りのみ。下りは評価しない)。15%以上は警告だけで、除外はしません。橋・トンネルと確認できた区間だけ、両端の標高を直線で結んで補正します(根拠のない急勾配は消しません)。
  - 景観(推定): OSMの展望地・山頂・峠・川・湖・海岸との近さ。森林・山並みは評価していません。
  - 通行止め・自転車で走れない候補は、スコアに関係なく選びません。通行止めの回避を距離の上限より優先し、超えたときは理由を表示します。
- **共通探索(全条件)**: 通常の検索は /route 1回。基本の候補に改善の余地があるときだけ、自動で経由地(峠・景観・自転車ルート)や除外点(急坂・交通の多い区間)を足して再探索します(追加の /route は最大3回・2段階・20秒まで)。経由地は、/locate で自転車で通れる道に載ると確認できたものだけ使います。AIは使いません。結果は「取得できた候補の中での最良」で、最適解を保証するものではありません。開発用: `localStorage.setItem('rt-explore','0')` で追加探索を止められます。
- 交通量・景観はいずれも推定です。実際の道路状況・通行止めは必ず公式情報で確認してください。
- 通行止めは自動取得できないため、地図上に手入力で登録し、その道路を避けて再計算します。

## 実APIの診断(開発用・route-v57)

通常の画面には出ません。アドレスの末尾に `?rtdiag=1` を付けて開いたときだけ、画面の下に診断パネルが出ます(例: `…/route/index.html?rtdiag=1`)。「診断を開始」を押すまで通信しません。

- やること: 実際の Valhalla(`/route`・`/locate`・`/trace_attributes`)と Overpass に、アプリの実際の処理で、4つの条件(最小獲得標高・最大獲得標高・自転車ルート優先・快適・絶景)と、経由地つきの快適・絶景を順番に問い合わせ、応答の形・回数・時間・エラー・取得できた属性を JSON にまとめます(「JSONを保存」「コピー」)。
- 判定は、確認できたものだけ「OK」。通信できなかった・その場面が起きなかったものは「未確認」とし、成功にしません。
- 負荷: 1回だけ、順番に実行(場面の間は約1.5秒あける)。Valhalla は最大40回で止め(実機の1回の診断では23回だった)、HTTP 429 を受けたら中止。直後の再実行は受け付けません。
- 守ること: 利用者の保存済みの地点・通行止め・APIキーは使いません(診断用の固定地点。パネルで書き換え可)。結果には座標もキーも入れません(出力の自己点検あり)。診断中と、そのページを閉じるまで、端末への保存(localStorage・RTStore)を止め、前後で保存内容が同じことを結果に記録します。「終了」で通常の画面に戻ります。
- 取り外し: `route/diag.js`、`index.html` の `RT-DIAG:BEGIN 〜 RT-DIAG:END`(3行)、`tests/diag.test.js`、`tests/e2e/diag-flow.pw.py` を消すだけです。Service Worker の事前キャッシュには入れていません。

### 実機診断を受けた調整(route-v57)
- 橋・トンネルの補正: 位置は、`/trace_attributes` の照合結果の形状(`shape` と `begin/end_shape_index`)で重ねる(辺の長さの比例配分は、実測で最大89mずれた)。両端を標高データの1画素分(z13で約15m)広げる(短い橋で10〜38%の偽の急勾配が残ったため)。補正するのは橋・トンネルの区間とその1画素だけで、それ以外の標高は変えない。
- 景観V: 展望地・山頂・峠は「距離で重みを付けた数 ÷ km」、水域は「距離で重みを付けた割合」を、頭打ちしない連続値にした(以前は全候補が1.0になった)。配分 0.4/0.6、総合の重み 45/35/20 は変更なし。基準値は仮置き。
- Overpass: 予備の接続先(応答なし)を外し、1回30秒で打ち切る。最大獲得標高で峠のデータが取れないときは、基本の候補を返し「追加探索は行っていません」と表示する。
